# 3D Pose Audio Radar

## ローカル開発

Node.js 24 と npm を使用します。

```sh
npm install
npm run dev
```

`npm test` で回帰テスト、`npm run lint` で型検査、`npm run build` で本番用の `dist/` を生成します。プルリクエストでもこれらを自動実行します。

開発サーバー起動前とビルド前に、インストール済みの MediaPipe パッケージから WASM・ローダーを `public/mediapipe/wasm/` にコピーします。これにより JavaScript と WASM のバージョンを揃え、アプリと同じドメインから配信します。生成ファイルは Git 管理対象外です。モデル本体は起動時に `storage.googleapis.com` から取得します。

スウィープは周期変調ホワイトノイズで利用できます。短い時計音・足音は固定位置で提示します。必要なランドマークの可視性が低い場合は方向の更新を止めます。頭部モードは鼻・両耳、肩モードは両肩、複合モードは両方を必要とします。肩幅連動距離では両肩も必要です。背面などで顔が隠れる場合は肩モードを選択してください。

## GitHub Pages

`.github/workflows/deploy-pages.yml` が `main` へのプッシュ時に型検査・ビルドを行い、成功した成果物を GitHub Pages にデプロイします。Actions タブから手動実行もできます。追加のデプロイ用シークレットは不要です。

リポジトリの **Settings → Pages** で以下を設定してください。

- **Build and deployment → Source**: **GitHub Actions**
- **Custom domain**: `pose-audio-radar.moukaeritai.work`（設定済みなら維持）
- 証明書の準備後に **Enforce HTTPS** を有効化（カメラ API の利用に必要）

公開先は https://pose-audio-radar.moukaeritai.work/ です。カスタムドメイン直下に配信するため、Vite の `base` は標準の `/` を使います。`public/CNAME` はビルド時に `dist/CNAME` へコピーされますが、Actions によるデプロイでのカスタムドメインは Settings → Pages で管理します。

## WHENet 頭部モード（実験）

停止中に「姿勢検出モデル」で **WHENet** を選び、カメラを起動します。YOLOX Nano が頭全体を自動検出し、WHENet がその切り出し画像から yaw・roll・pitch を推定します。肩・複合モードと肩幅連動距離は無効になり、距離は2.5m固定です。MediaPipe に戻すと、それまでの基準モード・距離設定を復元します。

- 最大の検出頭部1つを対象とします。1人で使用してください。人物の同一性を追跡する機能はありません。
- 紫色の枠は頭部検出結果、`HEAD DET` は検出器のスコアです。角度推定の信頼度ではありません。
- 検出スコア0.5未満・頭部未検出・カメラ映像が1秒以上更新されない場合は、既存の未検出時音声処理に切り替えます。推論が遅くてもカメラが動いていれば結果を採用し、結果の更新が観測した処理時間の2倍（最小1秒・最大30秒）以上止まった場合は未検出扱いにします。
- 推論は Web Worker 内の ONNX Runtime で行います。標準では WebGPU を優先し、使用できない場合は WASM（CPU）へ切り替えます。1度に処理するフレームは1枚で、停止・カメラ切替前の結果は破棄します。カメラ画像のサーバー送信はありません。映像は長辺640px以下の画素データとしてワーカーへ転送し、GPU の映像テクスチャの受け渡しには依存しません。
- 初回起動時のモデル・実行ファイルは合計約50 MB（展開後）。GitHub Pages と同じドメインから読み込み、COOP/COEP ヘッダーや SharedArrayBuffer は不要です。Web Worker・OffscreenCanvas・WebAssembly SIMD が必要です。
- WHENet の元デモの回転行列を逆変換して、頭部から見たカメラの方向を音にします。画角は水平60°・垂直45°の近似です。頭部の角度、特に横顔・後頭部での精度、実カメラでの左右と上下の一致、スマートフォン上の速度は実機での比較が必要です。

低速な端末では `0.4 FPS` のように小数表示し、推論時間も表示します。初回の結果が返る前は「映像の取り出し・転送」「頭部検出」「角度推定」の進行状況を表示します。各工程が30秒を超えると工程名付きのエラーで停止します。推定に1秒以上かかる場合、動きに対して音が遅れるため、速い追従が必要なら MediaPipe を選んでください。

### GPU 実行

停止中の「WHENet の実行方式」で以下を選べます。設定はブラウザに保存します。

- **GPU 優先（標準）**：Worker 内で高性能側の WebGPU アダプターを要求し、選ばれたデバイスを両モデルに明示的に渡し、両モデルのセッション作成と試行推論を行います。WebGPU 未提供・アダプター未取得・ソフトウェアアダプターの場合は CPU を使います。対応演算は GPU、未対応の演算（頭部検出の NMS など）は ONNX Runtime の CPU カーネルで処理します。
- **CPU 固定（比較用）**：GPU を試さず、両モデルを WASM の1スレッドで実行します。同じ姿勢・計測回数で GPU 優先と比較できます。

Windows では、HTTPS 上で WebGPU に対応した Chrome／Edge と、GPU を使用できるブラウザ・ドライバー環境が候補です。API の有無だけで GPU 使用とは判定しません。カメラ欄の「検出 GPU/CPU・角度 GPU/CPU」と、診断パネルの実行方式・CPU を使用する理由を確認してください。GPU 情報はブラウザから提供された範囲で記録します。ベンチマーク開始時の実行方式も結果に保持するため、後から設定を切り替えても結果の条件を確認できます。速度向上の程度は GPU・ドライバー・ブラウザに依存します。

GPU の初期化・試行推論・実行に失敗したモデルは CPU に切り替え、実行時の失敗では同じ入力を CPU で1回再実行します。GPU デバイス喪失も監視します。CPU でも失敗した場合は既存のエラー表示で停止します。応答が戻らない場合の既存タイムアウトは引き続き有効です。実行途中の切替ではベンチマークを中断し、通常の計測履歴も新しいグループにします。切替処理を含む最初のフレームは通常集計から除外します。

GPU の試行推論・シェーダー準備は起動時間に含まれます。ONNX Runtime 1.30.0 の WebGPU エントリーに対応する `ort-wasm-simd-threaded.asyncify.mjs/.wasm` を同じドメインから配信します。モデルの重みと入力解像度は CPU 経路と共通です。

### 開発者向け診断・ベンチマーク

WHENet を選択すると、カメラ欄の **「開発者向け：WHENet 診断・ベンチマーク」** を開けます。通常の追跡中も直近最大60回を記録し、開始後の初回を別表示します。高速化の前に、どの工程で時間を使っているかを調べるための機能です。

1. タブを前面に置き、頭全体を映してカメラを起動します。
2. 計測回数（5・10・20回）を選び「ベンチマーク開始」を押します。押した時点ですでに処理中のフレームは対象外とし、次の1回を慣らし、その後の指定回数を計測します。1回10秒の環境では5回計測でも約1分以上かかります。
3. 工程別の直近・平均・中央値・最大時間と実行回数を確認します。完了後のベンチマーク結果は固定され、通常の頭部追跡は継続します。「通常の診断に戻る」で直近履歴の表示へ戻れます。
4. 「診断 JSON を保存」で結果を取得します。停止・推論エラー後も保存でき、途中で止めたベンチマークは中断として残ります。再起動すると通常の履歴は新しい実行に切り替わります。

計測は `performance.now()` による経過時間で、CPU 使用率ではありません。主な読み方は次のとおりです。

| 時間が大きい工程 | 調べる対象 |
| --- | --- |
| 映像の縮小・画素取得 | カメラ入力、Canvas の描画・画素読み出し |
| 頭部検出モデルの実行 | YOLOX Nano の ONNX 推論 |
| WHENet モデルの実行 | 頭部角度の ONNX 推論 |
| 前処理・画像復元 | リサイズ、切り出し、RGB/BGR 配列変換 |
| 受け渡し・待機（差分） | スレッド間の配送、ブラウザによる実行待機など |

モデル実行時間はテンソルの作成・結果コピー・解放も含みます。「受け渡し・待機」は同じメインスレッドで測ったフレーム全体から、映像取得と Worker 内経過時間を引いて算出します。メインスレッドと Worker の異なる時計の原点を直接引きません。小さな負値は時計精度による誤差として0に丸めます。描画コールバックの最大間隔は処理時間と重なる参考値で、工程の合計に加えません。

頭部未検出では WHENet を実行せず、その時間は0ではなく未実行（JSON では `null`）として平均から除きます。表の各工程の回数が異なる場合、列の平均値を足しても全体平均にはなりません。未検出・背景タブ・映像更新停止の回数も表示するため、同じ条件の計測同士で比較してください。慣らしで頭が未検出だった場合、最初の WHENet 実行が本計測に入る可能性があります。

モデル取得＋セッション作成＋GPU 試行推論はフレーム処理から分離して表示します。JSON には ONNX Runtime のバージョン、モデル別の実行方式（WebGPU または WASM）、CPU への切替理由、入力解像度、ブラウザ情報、論理プロセッサ数、WebGPU API の有無、各フレームの計測値を保存します。WebGPU API の存在と実際の実行経路は別に記録します。CPU 部分は1スレッドです。映像・音声・頭部座標は保存・送信しません。初期化の速度とブラウザキャッシュの有無はこの計測だけでは分離できません。

### モデルの取得・配信

`npm run dev` / `npm run build` の前処理で `scripts/prepare-whenet.mjs` を実行します。WHENet（約17 MB）と YOLOX Nano の配布アーカイブ（約253 MB）を取得し、SHA-256 を検証して必要な頭部検出モデル（約3.8 MB）だけを抽出します。初回ビルドには `tar` と外部への HTTPS 通信が必要です。Node.js の `--use-env-proxy` を指定しているため、クラウド環境の `HTTPS_PROXY` 設定も利用します。モデル・WASM は Git 管理せず、生成した `public/whenet/` を Pages 成果物に含めます。

再ビルド時はキャッシュしたモデルもハッシュ検証し、破損していれば再取得します。GitHub Actions でもこのディレクトリをキャッシュします。取得先は `github.com` / GitHub Release のリダイレクト先と `s3.ap-northeast-2.wasabisys.com` です。ダウンロード失敗やハッシュ不一致ではビルドを失敗させます。

出典・ライセンスは [NOTICE](public/licenses/whenet/NOTICE.txt) と同ディレクトリに収録しています。モデルの取得URLとハッシュは準備スクリプトに固定しています。変換済み WHENet の出力順 `yaw, roll, pitch` は、元の `WHENet.h5` の Dense 重みと ONNX の重みを照合して確認しました。

### 検証

`npm test` は前処理、頭部選択、角度の座標変換、単一フレームの非同期処理、未検出・古い結果の無効化、停止後の遅延結果の破棄、モデル読み込み失敗後の再試行を検証します。

Chromium 154 / Linux の配信用ビルドで、公式 WHENet の2つのサンプル画像を仮想カメラ入力にした実モデル推論を確認しました。正面側・後頭部側で自動検出、空画像で未検出、カメラ停止後のトラック解放、モデル切替と再起動が成功しています。これは動作確認であり、角度精度や実カメラ・モバイル端末の性能検証ではありません。

WebGPU 経路は実 GPU のないクラウドで SwiftShader を使って機能確認しました。同じ正面サンプルの CPU 比較では、頭部枠がほぼ一致し、yaw・pitch・roll の差は最大約0.004°でした（このサンプルでの数値一致の確認であり、推定精度の評価ではありません）。ソフトウェアアダプターを許可するテスト用の注入は本番コードには含めず、製品の GPU 優先ではソフトウェアアダプターを避けます。この検証で GTX 1060 等の実 GPU における速度向上を実証したとは扱いません。
